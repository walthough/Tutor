# Basis for software engineering teaching choices

Use these sources for rationale, not as a script to recite during lessons.

- [Margulieux, Morrison & Decker (2020), Reducing Withdrawal and Failure Rates in Introductory Programming with Subgoal Labeled Worked Examples](https://link.springer.com/article/10.1186/s40594-020-00222-7): a semester-long programming study supports labeling meaningful solution subgoals. It improved initial quiz performance and reduced failure/withdrawal, but did not improve average exam scores. Use examples as scaffolding, then check learner application and transfer.
- [Bisra et al. (2018), Inducing Self-Explanation: A Meta-Analysis](https://link.springer.com/article/10.1007/s10648-018-9434-x): supports asking learners to explain relationships and solution steps. This is broader learning evidence, not proof of an optimal software tutoring script; inspect the learner's explanation for misconceptions.
- [Freeman et al. (2014), Active Learning Increases Student Performance in Science, Engineering, and Mathematics](https://pmc.ncbi.nlm.nih.gov/articles/PMC4060654/): synthesis favors active learning over traditional lecturing in undergraduate STEM. Supports learner activity rather than lecture alone; it does not isolate this skill's exact task sequence or establish effects for all professional engineering training.
- [Cepeda et al. (2006), Distributed Practice in Verbal Recall Tasks](https://pubmed.ncbi.nlm.nih.gov/16719566/): supports spacing for retention. Applying this to revisiting programming concepts is a design inference; delayed coding tasks are needed to assess retained application, and no particular coding-review interval follows from the verbal-recall findings.

Fading scaffolding, debugging hypotheses, runnable checks and realistic design constraints are practical instructional choices. The cited work supports parts of the approach; this tutor's complete workflow has not been experimentally validated.
